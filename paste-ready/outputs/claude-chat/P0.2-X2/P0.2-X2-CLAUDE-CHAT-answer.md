## Findings, ranked

### HIGH

**H-1 — §6.3 publication gate, D-44, CONTRACTS EXPORTED: the licence rule has no typed enforcement.**
- [Certain] No loader check ties `PublicationSwitch` to data licensing. MB-E1 to MB-E8 check approval fields, the audit record and the kill switch, never data licences.
- [Certain] `ProviderSelection` cannot express "licensed for publication" as distinct from "licensed for research."
- Failure scenario:
  - Counsel confirms SEBI RA registration.
  - The Owner records `PublicationSwitch(market=IN, enabled=True, legal_review_ref="LR-IN-1", …)` with a valid audit record.
  - OQ-68 is still open, but the set loads.
  - Signals built on Upstox bars publish. MB-AC-14 is breached.
- Minimal fix:
  - Export `publication_data_cleared(market, selections) -> bool` from this spec.
  - Add MB-E9 to the P1.3 loader: an enabled switch is rejected unless every selection feeding signals in that market is cleared.
  - Add a `licensed_use: Literal["none","research","publication"]` field to `ProviderSelection`. A forum reply must never be able to flip SELECTED for publication.

**H-2 — §8.1 `VendorSeriesSnapshot`, D-43: research-gate data can reach the signal path through storage.**
- [Certain] D-43 checks only `resolution == 1D` at signal entry. `v2/signals` may import `v2/research` (MODEL-B §4), and the snapshot carries no licence or provenance class.
- Failure scenario:
  - A research client running under `ResearchGateApproval` stores Upstox 1D snapshots.
  - P2.7 later reads that stored data.
  - Signal entry accepts it, because the resolution is 1D.
- Minimal fix: signal entry rejects any snapshot whose `(provider, capability, market)` selection lacks `licensed_use="publication"`. Add a test beside D-43's resolution test.

### MEDIUM

**M-1 — §8.3 THR-13: the Upstox budget is not shared across processes.**
- [Certain] The spec schedules the 1-minute backfill "around" the evening batch but gives no shared-state rule.
- [Likely] P2.1 will build each job with its own in-process `ClientThrottle`.
- Failure scenario:
  - Each job runs at 1,000 per 30 minutes and 25/s.
  - Together they reach exactly 2,000 per 30 minutes and 50/s, which is the documented limit with zero headroom.
  - One coincident burst returns `UDAPI10005`. PE-23 then stops every India row for the session and risks a vendor suspension.
- Minimal fix:
  - Keep the counters in Redis, keyed by `(provider, account, scope)`, using atomic INCR plus EXPIRE per window.
  - Alternatively, hold one runner lock per provider account.
  - Apply the same fix to Fyers THR-14.

**M-2 — §8.1 `ClientThrottle`: the documented limit is not bound to its fact.**
- [Certain] The field table says `documented_max_count` equals a `RateLimitFact.max_count`, but no validator enforces it.
- Failure scenario: `ClientThrottle(UPSTOX, "historical", 4000, 2000, 1800)` validates, and the client then runs at the real limit.
- Minimal fix: replace the field with `fact: RateLimitFact` and validate that provider, scope and window match.

**M-3 — PE-24, NB-31: candle order and duplicate candles are undefined.**
- [Certain] The Upstox V3 page states no candle order. Its sample for a 1-minute request shows two candles a month apart, so the sample cannot settle the question.
- Failure scenarios:
  - "Last returned session" is taken as `candles[-1]`, but the response is newest-first. The 5-session re-request then makes PE-24 fire every night and India goes dark.
  - A response carries a duplicate key. A dedup that keeps the first bar silently discards the vendor's correction.
- Minimal fix:
  - Define the last returned session as `max(session_date)`.
  - Treat any duplicate key or non-monotonic sequence as PE-13.

**M-4 — §8.1 `ResearchGateApproval`: no revocation or expiry.**
- [Certain] E-35 checks only that an approval record exists.
- Failure scenario:
  - Upstox answers OQ-68 "not permitted."
  - The existing approval stays valid, and the research client keeps restarting every night.
- Minimal fix: add `revoked_on: date | None`, and make E-35 reject a revoked approval. Recording a negative OQ-68 answer revokes the approval.

**M-5 — §6.3 research gate with SEL-12: gated news can reach a third-party LLM.**
- [Certain] One approval covers all PROVISIONAL Upstox rows, including News. OQ-76 (the licence to pass news text to an LLM) is open, and F-92 bars transmission without consent.
- Failure scenario: a P4 research step sends Upstox news headings and summaries to DeepSeek under the gate.
- Minimal fix: either exclude SEL-12 from the gate until OQ-76 closes, or rule that no gated content goes to an external LLM.

**M-6 — NB-34, NB-35, §5.14: tick and lot size still point at Kite's dump.**
- [Certain] D-39 removed Kite from every data row, so the reference is stale.
- [Certain] The replacement Upstox master is ambiguous: its JSON equity sample shows `tick_size` 5.0 while the CSV sample shows 0.05.
- [Likely] 5.0 is in paise.
- Why it matters: MODEL-B ND-4 rounds every stop down to the master tick, and the position weight is computed from the rounded stop.
- Failure scenario: a stop of ₹101.37, read against a tick of "5.0 rupees", rounds to ₹100.00. The model weight is then wrong.
- Minimal fix:
  - Point NB-34 and NB-35 at the Upstox master, with the Fyers master as a cross-check.
  - Use the tick only when both masters agree after unit normalisation. Otherwise publish no signal for that instrument (INV-6).

### LOW

- **L-1, §0 and `depends_on`.** The PDT paragraph and the SPEC-CR1 dependency fall outside issue #2's scope. The paragraph also states a FINRA rule change dated 2026-06-04 with no F-row. Delete both, or cite the change.
- **L-2, §0 vs UP-40.** §0 says Fyers introduced "this plan structure" on 2026-10-16. UP-40 correctly says F-98 does not date the Standard history window. Align §0 with UP-40.
- **L-3, F-82 and UP-41 paraphrase.** Two slips, neither of which changes the conclusion:
  - Section 2 also contemplates a platform offered to the public, not only to FYERS clients.
  - Section 15 says FYERS shall delete cached and stored content. The spec reads this as a client duty.
  - OQ-68 should quote both clauses verbatim for counsel.
- **L-4, F-43.** BQ-48 rests on this fact at PRIMARY_EXTRACT level. I read the page in full and it matches, so upgrade the level to PRIMARY_FULL.
- **L-5, §5.4 Auth.**
  - The page lists Charges, Margins, Option Chain and IPO as needing no static IP as well.
  - The same token can read User, Portfolio and other account APIs once a static IP is whitelisted.
  - That makes the path allowlist the only barrier between this credential and the Owner's holdings.
  - Add an MB-AC-4 test asserting the allowlist rejects `/portfolio`, `/user`, `/charges` and `/margins` paths.

## Owner questions (not defects)
