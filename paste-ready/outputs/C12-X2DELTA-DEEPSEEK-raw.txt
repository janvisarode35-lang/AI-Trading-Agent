## 2. Did any fix introduce a new defect or fail-open path?

### D-1 — BLOCKER — `_leaves` refuses legitimate keys with a literal `.`, `[`, or `]` in **rule field names**

**Where.** `_leaves` at diff l. ~825–831. The check `set(k) & set(".[]")` applies to **every mapping key**, including keys inside `rules` and inside `inputs`/`exempts`/`allowed_values` mappings.

**Failure scenario.** `PolicyDocument` is `extra="allow"`. A rule may legitimately have `modify.target = "some.quantity"` (a dotted target name) or an `inputs` entry whose value is a **mapping** with a key like `"a.b"`. If such a value ever appears, `_leaves` refuses the *whole document*, not just the offending path. That is fail-closed (no change is applied), so it is not a fail-open — but it is a **denial of service on legitimate configuration**: the spec §3.7 says every leaf outside `rules` is classified by `CONFIG_KEY_DIRECTIONS`; it does not say keys inside `rules` must be dot-free. `_leaves` is called on **both** sides of the diff at `_config_changes` (l. ~888) and at `_rule_field_changes` (the diff does not show, but the `_SET_FIELDS` change to `_members` is inside the rule path).

Concrete input that breaks it (assuming `inputs` can carry a mapping — **Q-6**): `_edit("EXP-001", inputs=[{"a.b": 1}])` raises `PolicyDiffError` on an otherwise valid rule edit. If the rule schema forbids mapping inputs, this is unreachable; I cannot see the rule model in the diff.

**Severity: BLOCKER if rule inputs can be mappings; MEDIUM otherwise.** Fix: scope the refusal to keys **outside** `rules` (pass a flag or a different prefix), or only refuse when the offending key is at the top of a path that will be compared by dotted string — the classification is per dotted key, and rule paths are `rules.<id>.<field>` so a dot inside a *value* is fine. Minimal fix: in `_leaves`, only enforce the refusal when `prefix == ""` or `prefix.startswith("rules.") is False`.

### D-2 — HIGH — `_members` for `inputs` no longer catches the `["a,b"]` vs `["a","b"]` collision the X2H-2 fix claimed

**Where.** `_predicate_records` at diff l. ~620–636. `a, b = old.allowed_values, new.allowed_values`, then `_set_move(a, b, ...)` compares `_members`. `_identity("a,b")` returns `("str", "a,b")`; `_identity("a")` returns `("str", "a")`. Two distinct members → distinct sets. **Closed.** I withdraw the earlier D-2 concern: `_members` is injective and `_set_move` compares on it. The `_as_set` calls are display-only now. **X2H-2's set-collision case is closed.**

But `_SET_FIELDS` still includes `inputs`, and `_differs` now uses `_members` for it. `t_order_is_not_a_change` tests reordering of `inputs`, `exempts`, `allowed_values_emergency`, and `allowed_values` — all pass by set semantics. **Closed.**

### D-3 — BLOCKER — `_threshold_record`'s new `else` misclassifies `IN`/`NOT_IN`/`EXISTS`/`MULTIPLE_OF` thresholds

**Where.** `_threshold_record`, diff l. ~595–599. The old `elif comparison in _MIN_VALUE:` was removed; the final `else` now handles **any** comparison not in `_MAX_VALUE`. That includes `IN`, `NOT_IN`, `EXISTS`, `MULTIPLE_OF`, `EQ`, `NE`, and any future comparison.

**Failure scenario.** A rule with `comparison = "in"` and `threshold = 5` changed to `threshold = 3`:
- Old code: `C-04` "no ordered comparison", `UNDECIDABLE`, → two-person.
- New code: `comparison not in _MAX_VALUE` → `else` branch → `d = TIGHTENS if y > x else LOOSENS if y < x else NEUTRAL`. `5 → 3` is `y < x` → `LOOSENS`. **One-person, free.**

That is a **fail-open**: a loosening of a predicate threshold that has no ordered semantics is now classified as a loosening with the *lowest* approval count. The spec §C-04 / the prior X2H-11 text says the branch was unreachable because "`(m, None)` is always in the set and is checked first" — but that reasoning applied to `_compare_anchor`, not `_threshold_record`. The `_threshold_record` branch **is reachable** for every rule whose `comparison` is set-valued. If `t_every_comparison_is_ranked` (or `_NO_CONSTANT`) guarantees no rule uses `IN` with a numeric `threshold`, this is unreachable at runtime — but §8's "A bound is a token on one side and a number on the other ⇒ UNDECIDABLE (C-05)" and C-10/C-13 suggest the schema tolerates combinations. **BLOCKER** until the author produces the invariant "no rule with `comparison in _NO_CONSTANT` has a non-null `threshold`" as a test, or restores the `elif comparison in _MIN_VALUE` and a final `else` with `C-04`.

The minimal fix is one line: change `else:` back to `elif comparison in _MIN_VALUE:` and keep the final `else: out.add(..., UNDECIDABLE, "C-04", "no ordered comparison")`. The diff shows the `else` was added *because* X2H-11 said it was dead; it was not dead.

### D-4 — HIGH — the single try around the three store reads wraps an adapter whose `request_used` may be a **write**

**Where.** `assert_authorisation_current`, diff l. ~1281–1295.

**Failure scenario.** `IN_FORCE_STORE.request_used(conn, auth.request_id)` is a **read** per §5.3 step 2, but a future adapter could implement it as a write (an idempotency key insert). If `request_used` succeeds (writes) and `database_time` **fails** (e.g. a transient connection error after the insert but before the clock read), the whole try catches `Exception` and raises `InForceAnchorError`. The idempotency key is now **written but the request was never applied** — a subsequent retry sees `request_used == true` and raises `StaleAuthorisationError`. The approval is consumed without any version being applied. **Fail-closed in the sense that nothing is applied, but it silently burns an authorisation.** The spec §5.3 step 2 says "This comes first, so a replay at any age writes nothing" — that ordering is preserved — but the write on a failing path is new.

More importantly: the try wraps `in_force_hashes`, `database_time`, and `request_used` **together**. If `request_used` raises (e.g. transient), the exception is caught and `used` is undefined — the `if used:` below is never reached, and `InForceAnchorError` is raised. That is correct (nothing applied). But if `in_force_hashes` returns an empty dict, the `if not stored:` check is **outside** the try and fires before `request_used` is called — good, the store's no-rows case is reported before a request is burnt. **OK.**

The real risk: **ordering**. §5.3 step 2 says "**Refuses a used request** (X2F-1, X2G-2) … This comes first". The code now calls `in_force_hashes` and `database_time` **before** `request_used`. That is a spec deviation: the store read and clock read must precede the used check per the code, but §5.3 step 1 (read store) precedes step 2 (used), so the order is actually spec-compliant. **Withdraw.** But the spec §5.3 says step 2 comes **after** step 1 and **before** step 3 (expiry), which is what the code does. **No finding.**

Residual: the `except Exception` catches a **`PolicyGovernanceError`** if the adapter raises one (e.g. a store that verifies a signature). That would be re-wrapped as `InForceAnchorError` and lose the original type. §8 lists `PolicyGovernanceError` separately. **MEDIUM**: in the try, `except (PolicyGovernanceError,) as exc: raise` before the broad `except Exception`. Or list it as an OPEN QUESTION Q-7: can the store adapter raise `PolicyGovernanceError`?

### D-5 — HIGH — `_compare_anchor` now silently accepts a missing `(m, None)` anchor

**Where.** `_compare_anchor`, diff l. ~1237–1243. The three lines
```
base = (diff.market, None)
if base not in stored:
    raise StaleAuthorisationError(...)
```
were replaced by `anchor = stored.get((diff.market, None))`.

**Failure scenario.** An `(m, None)` row is missing from the store (e.g. the genesis row for US was deleted by an operator, or the store returns a partial map). Old code: `StaleAuthorisationError` — nothing applied. New code: `anchor = None`. The subsequent comparison (not shown in the diff — **Q-8**) presumably does `if stored.get(combo) != anchor:` → `stored.get(combo)` is `None` for a new combo, `anchor` is `None`, `None != None` is `False` → **passes**. The `(m, e)` combination with no stored row is now **anchored by nothing** and is accepted.

This is exactly the fail-open the old `raise` prevented. The comment says "the two are one effective document with one hash (measured)" — that measurement assumed the `(m, None)` row **exists**. If it is missing, the two are not one effective document; one of them does not exist.

**Input that breaks it.** `FakeStore` whose `in_force_hashes` returns `{("US", None): <hash>}` but not `{("US", "paper"): ...}`; `auth.diffs` has a `PolicyDiff(market="US", environment="paper", changes=(a LAYER_ADDED for `policy.env.paper`,))` whose `old_content_hash` is **wrong**. The old code raises because `("US", None)` exists but the anchor hash differs. The new code also raises because the anchor hash differs. **Not a break** for that input.

**The break** is: `in_force_hashes` returns `{("IN", None): <hash>}` but **no `("US", None)` row**, and `auth.diffs` has a US `(US, "paper")` diff with a `LAYER_ADDED`. The `derive_combinations` set includes `("US", None)` and `("US", "paper")` — so the union with stored has `("US", None)` with **no stored row**, which the previous step (step 4, "The set of combinations with a current in-force row, united with … must equal …") may already reject if `("US", None)` is not in the union. **Q-9**: does the set-equality check at the top of `_compare_anchor` reject a `(m, None)` combination with no stored row? If yes, `stored.get((diff.market, None))` can only return `None` for a stored row that the set check already rejected — **unreachable, and the fix is harmless**. If the set check is per-`(m, e)` and the `(m, None)` row is exempted (as it must be, since `(m, None)` is the base), then `None` is reachable and the fix is a fail-open.

I cannot see the set-equality check. **This is a HIGH pending Q-9.** The minimal fix if reachable: `anchor = stored.get((diff.market, None)); if anchor is None: raise StaleAuthorisationError(f"{combo}: no row for {(diff.market, None)} to anchor it")` — restore the three lines but with `.get`.

### D-6 — MEDIUM — `_kind` treats `Decimal("0.05")` and `0.05` as the same kind, but `_identity` treats them as distinct

**Where.** `_kind` (diff l. ~435–443) returns `"number"` for `int`, `float`, `Decimal`, and **not** `bool`. `_identity` (diff l. ~380–405) returns `("number", str(Decimal(str(v))))` for the same three. For `Decimal("0.05")` vs `0.05`, `_kind` equal, `_identity` both `("number", "0.05")` — **equal**. So a change from YAML `0.05` (parsed as `float`) to `Decimal("0.05")` is **not** a change. That is the intended `C-03` "same number, re-represented" case. **OK.**

But `_kind(True)` is `"bool"` and `_kind(1)` is `"number"`; `_identity(True)` is `("bool", True)` and `_identity(1)` is `("number", "1")`. Distinct — good, no X2H-2 regression. **Closed.**

### D-7 — MEDIUM — `_identity` for `float("nan")` and `float("inf")`

`Decimal(str(float("nan")))` raises `decimal.InvalidOperation` on some Python versions, or returns `NaN`. If a config value is `nan` (YAML `.nan`), `_identity` may raise inside `_config_changes`. That is caught by `_load`'s `except Exception` if `_config_changes` runs inside the load — but `_config_changes` runs in `diff_policies`, not `_load`. **OPEN QUESTION Q-10**: is `diff_policies` wrapped to map any exception to `PolicyDiffError`? §8's catch-all says it must be. If not, `nan` escapes as `decimal.InvalidOperation`. Fail-closed but wrong type.

### D-8 — LOW — `_members(old) or frozenset()` collapses `None` and empty

`_set_move` at l. ~460: `a, b = _members(old) or frozenset(), _members(new) or frozenset()`. `_members(None)` returns `None`, `None or frozenset()` is `frozenset()`. `_members([])` returns `frozenset()`, `frozenset() or frozenset()` is `frozenset()`. So `None` and `[]` compare equal in `_set_move`. But `_config_value`'s set branch checks `isinstance(old, (list, tuple))` **before** calling `_set_move`, so `None` is refused there with C-39. The `_set_move` call is only reached with lists. **Unreachable in the config path.** In `_predicate_records`, `_set_move(a, b, ...)` is called with `a, b = old.allowed_values, new.allowed_values` — which can be `None` if the field is optional. Then `None` and `[]` compare equal → NEUTRAL. That is the correct `§2 row 7` behaviour for an empty set vs absent, but it is a **silent default of a missing value** in the comparison. **LOW**: use `_members(None) is None` distinctly. Not a fail-open because the `_differs` check already fired to reach this branch, and `_differs` uses `_members` (injective, `None != frozenset()`). **Closed.**

### T-1 — HIGH — `t_keys_come_from_the_in_force_base` cannot fail for the F30 mutant

Already covered in X2H-3 above. The test asserts `raises(...)` on `(CD, ZZ)` when the layer map is `(CD, ZZ)` and the base is `(AB, JS)`. The **correct** code reads `_load(old_dir, None, None)` → `(AB, JS)` keys → `(CD, ZZ)` is "not listed" → raises. ## 4. Concurrency, correctness, security (delta scope)

- **No new shared mutable state** in the diff. `_parsed` in the test suite is still a module-level dict, but tests are single-threaded.
- **Float for money:** `_identity` now uses `Decimal(str(v))` for `float`/`int`/`Decimal`, which is the correct comparison form. But `_config_value`'s numeric branch (not in the diff) still decides direction — **Q-1** applies there. No new float-for-money in the diff.
- **Naive datetimes:** the new `t_store_failures` passes a naive `datetime.now()` and expects `InForceAnchorError`. That is the correct test. No new naive datetime in production code.
- **Security:** `t_loader_failures_are_refused` writes `b"\xff\xfe\x00"` to `policy.yaml`. The `_load` catch turns a `UnicodeDecodeError` into `PolicyDiffError`, which is what §8 says. No secret in a log added.
- **Resource:** `_identity` on a deeply nested structure recurses; no bound. A malicious `policy.yaml` with 10^5 nesting levels is a stack overflow. The loader's YAML parser will hit its own recursion limit first (PyYAML raises `RecursionError`), which `_load`'s `except Exception` catches. **Closed** for the load path; **unreachable** for the config path if the load always precedes.

## 6. Verdict

**REJECT.**

Single reason: **D-3 — `_threshold_record`'s replacement of `elif comparison in _MIN_VALUE` with `else` is a reachable fail-open.** A rule whose `comparison` is one of `IN`, `NOT_IN`, `EXISTS`, `MULTIPLE_OF` (i.e. any comparison not in `_MAX_VALUE`) now falls into the numeric-direction branch and yields `TIGHTENS`/`LOOSENS`/`NEUTRAL` instead of the spec-mandated `UNDECIDABLE` (C-04). A `5 → 3` change on such a rule is classified `LOOSENS` and, under the approval ladder, needs one identity, not two. The prior X2H-11 called this branch dead; it is not dead on the `_threshold_record` path, only on `_compare_anchor`. This is a change that loosens a threshold with insufficient approval, on a live account, with a green suite and a green harness.

Secondary blockers to fix in the same pass: **D-5** (`stored.get((diff.market, None))` may accept a `(m, e)` combo anchored by nothing, pending Q-9) and **T-6/Q-11** (a C-40 test that may be a tautology). **D-1** is a BLOCKER if Q-6 says `inputs` can be a mapping.
