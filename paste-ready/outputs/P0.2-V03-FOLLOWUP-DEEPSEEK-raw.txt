**Defects found**

**1. `t_research_gate_is_closed_by_default` — BLOCKER (script, `sel["SEL-4"]` / `sel["SEL-10"]`).**
The script passes `ProviderSelection` objects into `research_gate_open`. `SEL-4` is `PROVISIONAL` and `primary=UPSTOX`, so `research_gate_open(ok, sel["SEL-4"], TODAY)` must be `True`. `SEL-10` is `BLOCKED`, so it must be `False`. Both hold. **But `SEL-4` carries `blocked_by=("OQ-39","OQ-68","OQ-69")` and status `PROVISIONAL` — the function accepts it.** The gate is documented as "one approval covers all PROVISIONAL Upstox rows." That means the gate opens for SEL-4 even while OQ-68 (the licence question) is unresolved, because `blocked_by` is not consulted. The name of the fix — "a BLOCKED row stays closed" — closes BLOCKED but not the more common case of PROVISIONAL-with-OQ-68. That is the default state of every India data row. Concrete input: `research_gate_open(ResearchGateApproval(approved_by="Owner", approval_ref="r", approved_on=date(2026,1,1)), sel["SEL-4"], date(2026,10,31))` → `True`, but SEL-4 depends on OQ-68 which is unresolved. Section 6.3 prose says the gate "is not on a BLOCKED row, and not on Fyers before OQ-68 is answered for Fyers" — it does **not** exclude Upstox rows blocked on OQ-68. Either the prose is wrong (should say: never on a row whose `blocked_by` names OQ-68) or the code is. This is the same class of defect the original review found in `publication_data_cleared`. Fix: `research_gate_open` must reject any selection whose `blocked_by` is non-empty, or specifically names `OQ-68`.

**2. `t_publication_needs_a_licence_record` — HIGH (script, "record without a licence" case).**
The case `{"licensed_use": LicensedUse.NONE}` leaves `licence_audit_id=AUDIT` in the merged kwargs (`good` includes it). The validator requires `(licensed_use is PUBLICATION) == (licence_audit_id is not None)`, so `NONE` + `AUDIT` is correctly rejected. Fine. **But no test exercises the reverse pair: `PUBLICATION` + `licence_audit_id=None`.** The "no record" case does (`licensed_use=PUBLICATION, licence_audit_id=None`) — that is covered. So both directions are tested. No defect; retract. Noting because I checked it.

**3. `t_one_row_per_key` — MEDIUM (script, `ProviderSelectionSet` uniqueness).**
`keys = [(s.capability, s.market) for s in self.rows]` — `market` can be `None` for market-less capabilities. Two market-less rows for the same capability (say two `MACRO` rows) collide on `(MACRO, None)` and are correctly rejected. **But** a market-less `MACRO` row and a `Market.IN` `MACRO` row do **not** collide. `_row_for` matches `s.market is market or s.market is None`, so for `Market.IN` it returns whichever row comes first in `selections.rows`. If the market-less MACRO row (say `FRED`, cleared) precedes an uncleared India MACRO row, `row_cleared(FRED, MACRO, IN, ...)` returns `True` against the market-less row even though a market-specific India row exists. Concrete input: `ProviderSelectionSet(rows=(MACRO/None/FRED/PUBLICATION/audit, MACRO/IN/UPSTOX/NONE))`, then `row_cleared(FRED, MACRO, Market.IN, s)` → depends on tuple order; if the market-less row is first, `True`. The fix must reject a market-less row when a market row for the same capability exists, or `_row_for` must prefer the exact-market row. Neither the validator nor the test covers this.

**4. `throttle_rows` parser — MEDIUM (script, `t_throttle_rows_are_half_of_the_limit`).**
`pairs = list(zip(re.findall(rx, limits), re.findall(rx, budgets)))`. If the THR-13 table's *limits* column reads `25 per second; 250 per minute; 1,000 per 30 minutes` (client values) and the *budgets* column reads the documented values, then `require(cli == doc // 2)` fails. If the columns are reversed — limits = documented, budgets = client — then it passes. The test asserts the second interpretation, but the diff does not show the table columns. **This is a check, not a defect** — it will fail loudly if the table is laid out the other way, which is the correct behaviour. No finding.

**5. `ProviderSelection.backup` on cleared rows vs SEL-4 — MEDIUM (spec, section 6.3 / `_row_for` / `row_cleared`).**
The new rule "a cleared row has no backup" is enforced only via the `ProviderSelection` validator. `cleared_rows()` in the test builds `backup=None`, so it passes. But `publication_data_cleared(Market.IN, selection_set())` runs against the real table where **SEL-4 (`eod_bars`, IN) has backup `Fyers`** and `licensed_use=NONE` — so it correctly fails today. Fine. The risk is future: if SEL-4 is ever marked `PUBLICATION`, the validator will reject it because it has a backup, and the operator has no obvious path other than splitting the row. That is fail-closed and arguably correct, but the spec does not say what the operator should do (drop the backup, or split the row into a primary-only publication row). Not a defect; add one sentence.

**6. `t_fact_counts` — LOW (script).** `got = sum(1 for l in rows if f"| {level} |" in l or f"| {level} (" in l)`. `F-84` reads `PRIMARY_FULL (staff forum post, not documentation)` — matches `PRIMARY_FULL (`. `F-43` now reads `PRIMARY_FULL (code samples excluded; read in full on 2026-10-30)` — matches. `F-108` reads `PRIMARY_FULL (code samples excluded)` — matches. If a future row says `PRIMARY_FULL(excluded)` without a space, the substring `PRIMARY_FULL (` will not match. That is a brittleness of the assertion, not a defect in this diff. No finding.
